# Document storage

This document defines Malum's first durable document-storage contract. It
covers the filesystem bundle produced from a successfully imported webpage. It
does not define the SQLite catalogue, HTTP API, author resolution, duplicate
handling, or frontend projection.

## Concepts

A Malum document is a stable library entity with an opaque identity. It is not
identified by its URL or by the bytes of one representation. URLs can redirect
or disappear, and the same material may deliberately be acquired more than
once.

Three independent descriptions prevent the word `source` from carrying
several meanings:

- **Acquisition method** records how material entered Malum. The first method
  is `url`.
- **Original format** records what Malum acquired and preserved. The first
  format is `html`, with the precise response media type recorded separately.
- **Reading kind** records the normalized reading experience. The first kind
  is `article`.

For example, a URL import and a future feed item may both contain HTML and
normalize to articles, despite having different acquisition methods. An HTML
file upload could likewise share the format and reading kind without claiming
to have been fetched from a webpage.

## Filesystem and SQLite responsibilities

Ordinary files preserve the acquired material and its normalized reading
representation. SQLite contains Malum's catalogue and author relationships;
later catalogue migrations will add search indexes and mutable reading state
when their behavior is designed.

Large HTML and image bodies do not belong in SQLite. Progress, author
associations, highlights, notes, inbox or archive state, and user metadata
overrides do not belong in ad hoc files inside the document bundle.

The bundle is an escape hatch for the document content; it is not a replacement
database for every Malum feature. A complete backup will eventually contain
both the SQLite database and the document directory.

## Data root and bundle layout

The storage package receives a data-root path from its caller. It does not
choose a development directory, deployment volume, or operating-system
location.

```text
<data-root>/
├── malum.db                         # SQLite catalogue
└── documents/
    └── <document-id>/
        ├── document.json
        ├── original.html
        ├── article.html
        └── resources/
            ├── <sha256>.png
            ├── <sha256>.jpg
            └── ...
```

Document IDs are random UUIDs generated by the storage layer. They are stable,
opaque identifiers: neither a URL nor a content hash is encoded into their
meaning.

All paths recorded inside `document.json` are slash-separated paths relative
to the document bundle. Absolute server filesystem paths are never persisted.

## Preserved original

`original.html` contains the exact response-body bytes returned for the
imported page. It is never rewritten, sanitized, or regenerated. Its checksum
and byte length are recorded in the manifest.

The original's format is `html`. Its precise media type, requested URL, and
final URL after redirects remain available separately; the format does not
erase that provenance.

## Normalized article

`article.html` contains Readability's cleaned article HTML. Image `src`
attributes whose resources were successfully stored are rewritten to relative
bundle paths such as `resources/<sha256>.png`. An unavailable resource retains
its remote URL.

This file preserves inline meaning and structures that the current typed reader
does not render. It remains untrusted HTML. Persistence does not authorize the
frontend to inject it without a separate sanitization policy.

The manifest contains the typed blocks and heading outline used by the reader,
along with extracted article metadata. Block image URLs retain their remote
provenance; the resource records map those URLs to local files when available.

## Manifest

`document.json` is UTF-8 JSON with a trailing newline. It is deliberately
human-inspectable and begins with a storage schema version. Version 1 records:

- `schemaVersion`, `documentId`, `readingKind`, and `storedAt`;
- acquisition method, requested URL, and final URL;
- the original format, media type, relative path, SHA-256 checksum, and size;
- the normalized article file's path, SHA-256 checksum, and size;
- title, raw extracted byline, site name, language, excerpt, publication and
  modification times, word count, reading-time estimate, and lead-image URL;
- typed article blocks and heading outline;
- raw byline and structured author candidates, excluding downloaded avatar
  bodies;
- stored and unavailable resource records;
- non-fatal ingestion warnings.

The initial categorical values are:

```text
acquisition.method = "url"
original.format    = "html"
readingKind        = "article"
```

The raw byline and structured author candidates are provenance, not internal
author identities. This bundle does not generate handles or create author
records. Downloaded author-avatar bytes are held for author-specific storage
and are not embedded in `document.json`.

## Resources

Each resource record retains its source URL and role. A successfully downloaded
resource additionally records a relative path, verified media type, SHA-256
checksum, byte length, and the status `stored`. A resource that could not be
downloaded has status `unavailable`, no local path, and remains represented by
its source URL and corresponding warning.

Stored resource filenames use:

```text
resources/<sha256>.<extension>
```

The extension is selected from the verified media type rather than trusted
from the remote URL. Identical resource bytes within one document share a file.
Resources are not deduplicated across documents: global deduplication would
complicate deletion, portability, and recovery without a demonstrated need.

An unavailable image does not make an otherwise readable document fail to
save.

## Atomic save contract

The writer creates a temporary directory alongside the final document bundles,
writes and checksums all files, writes `document.json` last, and then renames
the completed directory to the document ID. A successful return means the
complete final bundle exists. A failed return must not expose a partial final
bundle or overwrite an existing document.

Temporary directories are implementation details and are removed after a
failed save where possible. A future startup repair task may remove abandoned
temporary directories left by process or machine interruption.

The bundle is completed before a database transaction publishes it in the
SQLite catalogue. This ordering can leave a complete but unindexed bundle after
a database failure, which is detectable and recoverable. It avoids catalogue
rows that point at incomplete content.

The store can load a published manifest by document ID and open a stored image
only when its filename appears as a stored resource in that manifest. The HTTP
layer uses this checked boundary rather than joining client-supplied paths onto
the data root.

## Deferred decisions

- Canonical-URL matching, duplicate imports, and re-import versions.
- Catalogue recovery behavior for complete but unindexed bundles.
- Author reassignment, merging, and splitting interactions.
- User metadata overrides and export format.
- Frontend-safe HTML sanitization.
- Additional original formats, acquisition methods, and reading kinds.
- Global resource deduplication.
